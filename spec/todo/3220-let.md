## Let statement

**Priority:** P2
**Status:** wip — approved by the language designer
([Approval](#approval)); the one-variable loop, with its round trip, is
[#2854](https://github.com/functionalscript/functionalscript/pull/2854);
general bindings ([Later](#later)) are implemented but for a module's
variables and a `let` with no initializer, and the specification's
[variables](../bindings/variables/README.md) and
[loops](../control-flow/loops/README.md) pages describe the language as it
is; general loops remain

Introducing `let` and `=`, in one form first: the loop over one variable.

```js
export default n => {
    let r = 1;
    while (r < n) { r = r * 2; }
    return r;
};
```

### Problem

FunctionalScript expresses a loop one way: a `const` whose function calls
itself. Both serializers spell that as recursion, and V8 and Rust implement
no tail calls, so every loop a program writes overflows the stack after some
thousands of rounds in every output but one: JavaScriptCore, under Bun,
implements the tail calls ES2015 specifies, and one host of four is not
one a program can count on. The serializers can spell a tail
self-call as a loop again
([tail-call-loop](../../fjs/edag/todo/tail-call-loop.md)), which fixes the
functions written that way; it does not give the language a loop a reader
recognizes as one.

### Proposal

*The one-variable form below is what the approval covers, and the language
had until general bindings. Three of its refusals are superseded under
[Later](#later): a `let` with no `while`, an assignment outside a loop's
block, and the `while`'s adjacency to its `let` — the loop now steps the
one variable its block assigns, wherever that variable was declared. The
rest stands.*

Two statements of a block body, standing where a `const` may, that the
compiler reads as one loop — exactly the template the serializers
recognize, and nothing more:

```
statement ::= const | 'if' '(' value ')' block
            | 'let' id '=' value end | 'while' '(' value ')' loopBlock
loopBlock ::= '{' loopStatement* '}'
loopStatement ::= const | id '=' value end
```

- `let x = init;` declares the loop's variable with its initial value, and
  the `while` right after it runs its block while the condition is truthy,
  tested before each round as `?:` tests its condition.
- The block holds `const`s and assignments to the variable, `x = value;`.
  An assignment rebinds the variable for the statements after it, in
  order; the block's end continues the loop with the last binding, the
  variable unchanged where nothing assigned it. A value nothing after it
  reads — a `const` the block never uses, an assignment overwritten
  before any read, `r = null.x; r = 1;` — is established all the same,
  for what it does: it is an anchor of the block, as an unused `const`
  is anywhere, so the throw JavaScript throws there is thrown here. The
  writer writes such a value back as a `const` of the block, which is
  the same graph.
- From the loop on, `x` is a `const` of the body holding the value the last
  round left.
- One variable per loop, the `while` right after its `let`, no `break`,
  `continue`, guard, `return`, `throw` or nested loop in the block, no
  `let` anywhere else, no loop at the module level. Each is a later step,
  additive on this one, under [Later](#later).

**Lowering.** The loop is syntactic sugar and adds no node: `let r = init;
while (c) { s…; r = next; } rest` denotes `rest` with `r` the value of
`loop(init)`, where `loop` is `r => c ? (() => { s…; return loop(next);
})() : r` — the recursive spelling, its one parameter the variable, the
block the body of a parameterless function called where it stands, as a
guard's block is, so that a `const` in it is the block's alone and runs
only when the condition holds. The graph is the template
`['=>', 1, slots, ['?:', c, ['()', ['self'], [next]], ['arg', 0]]]` called
with `init`, a comma around the call where the block holds a `const` the
next value does not reach: the graph and hash a function written that way
has, and what the block reads from the body around it is the function's
frame, as any nested function's captures are.

**Refusals.** Three programs JavaScript admits are refused rather than
read another way, each because this reading and JavaScript's would
differ:

- a function nested in the loop, in its condition or its block, that reads
  the variable and is held as a value — a `const`, an item, an argument, a
  value returned — rather than called where it is written: JavaScript's
  closure sees the variable's last value, where the function's capture
  would hold the value of the round it was made in. A function called where
  it is written, `r = (() => r + 1)();`, reads the round's value in both,
  and is admitted: it is the one way source spells a scope in expression
  position, and the lowering inlines the call. The read is every enclosing
  function's up to the loop, so one held as a value is refused for a read
  a function it calls where written makes, `r = () => (() => r)();`, its
  closure outliving the round all the same.
  The initial value is read before the name is bound, as a `const`'s is,
  so a read of the variable there — `let r = r;`, or `let r = () => r;`,
  whose closure JavaScript lets see the variable's last value — is an
  unknown name, refused as any unknown name is (`const not found`): the
  lowering has no state for the initial value to read;
- a `const` of the variable's name in the block (`loop variable
  shadowed`): a block may shadow any other name, as a guard's block may
  ([bodies and guards](../control-flow/guards/README.md)), but the loop's
  block has one job, to assign the variable, and a `const` of its name
  declares that it cannot — JavaScript would throw on an assignment after
  it, as an assignment to a constant, and refuse a read before it, in the
  temporal dead zone. The round then leaves the state as it was, and the
  state being all the condition reads, every round after it is the same
  round: a loop that never ends, or throws at once. JavaScript runs that
  program; this compiler names the slip, a `const` written for the step,
  rather than compile a loop that cannot advance;
- an assignment to any other name, the one name a block may rebind.

A `let` not followed by its `while`, or a `while` no `let` stands before,
is refused: the two are one loop, and the refusal protects one guarantee,
that every `let` marks a loop's state, changed by the `while` right after
it and nowhere else. JavaScript admits `let x = init; use(x);`, and in
FunctionalScript it is `const` under another name — the same declaration
spelled twice, the second spelling asking every reader to search the scope
for an assignment that is not there ([DESIGN.md §12](../../doc/DESIGN.md#12-preserve-harmless-javascript-conventions):
the mistake prevented is a `let` left where `const` was meant). A `let`
assigned outside a loop is a variable, which no node of the graph holds:
the assignment is the loop's step, the one mutation that lowers to a pure
graph, so admitting the `let` and refusing only the assignment would read
a declaration one way and its use another. Both are refused by name,
`let without while` and `while without let`, rather than read as a
`const` or a variable ([DESIGN.md §10](../../doc/DESIGN.md#10-refuse-what-you-cannot-handle)).
The variable is a name of the body as a `const` is.

**Writers.** The source writer spells the template, called where it is
written in a function body, as the two statements, so a compiled module
runs in constant stack; the function text spells the template function as
the same `let` and `while` over a `let` of its parameter. Every writer has
the one loop spelling or the recursion, nothing else
([tail-call-loop](../../fjs/edag/todo/tail-call-loop.md)). The round trip,
`while` source to EDAG to `while` source to the same EDAG, is the proof
that the lowering and the spelling are inverses.

#### Benefits

- A loop that reads as one, in the JavaScript spelling every reader knows,
  and that runs the same under Node, in the compiled module and through the
  VM — no spelling a JavaScript engine reads differently is admitted.
- Constant stack in every output that recognizes the template, where the
  recursive spelling overflows on V8 and in Rust.
- No new node: the EDAG, its validators, interpreters and hash are
  untouched, and a hand-written tail-recursive function and the loop are
  one graph.
- The restriction to one template keeps the parser's lowering and the
  writer's recognizer inverses by construction, so the round trip is exact
  rather than argued.

#### Drawbacks

- The form is narrow. A loop over two variables, an early exit, or a
  `let` on its own are JavaScript the compiler refuses today, each for a
  later step rather than read another way.
- `let` means one thing only, the loop's variable; a JavaScript module
  using it elsewhere is refused.
- The text of a template function is program-visible, `String(f)`, and
  changes from the named function expression to the loop
  ([tail-call-loop](../../fjs/edag/todo/tail-call-loop.md)).
- Two keywords, four grammar rules, four frames in the fold, and one
  statement form in the writer: the complexity is the fold's, and it is
  bounded by the template.

#### General bindings

Milestone G allows `let` in every declaration position supported by the
source grammar, including modules, function bodies and nested blocks.
Preserve lexical scope, initialization and TDZ rules. After an uninitialized
declaration executes, its value is `undefined`.

- Locals and parameters use the same write-based classification: a binding
  is mutable if it is reassigned after initialization anywhere in its scope.
  Initialization, including defaults and destructuring, is not reassignment.
  A never-reassigned `let` and an unwritten parameter are both immutable and
  may be captured. Assignment to source `const` remains an error.
- A mutable binding cannot initialize a nested source function's frame.
  A nested read or write is a capture; nested assignment cannot mutate an
  outer binding. Classify all writes before checking captures, including a
  capture before a later assignment and syntactically unreachable writes.
  Check this before optimization removes writes or function boundaries.
- A function called where it is written — the callee of a call, through
  any depth of such functions — keeps reading a reassigned variable, the
  value of that moment, as JavaScript's does: the lowering inlines it, and
  the FunctionalScript writer spells a loop condition that shares a value
  as such a function, so the round trip depends on it. The proposal first
  planned to retire this admission with the uniform rule; it stays, for
  that reason, for reads: an assignment from inside such a function is
  refused, the inlined block holding values of its own that the scope
  around it never sees. A function held as a value — a `const`, an item,
  an argument, a value returned — is refused either way (`reassigned
  variable captured`).
- A `const` snapshot holds the current value and may be captured. It does
  not clone an object. Object-content mutation is the separate
  [mutability design](../design/mutability.md).
- `let` takes a pattern wherever `const` does: `let [a, b] = …` expands as the
  `const` pattern does
  ([destructuring](../bindings/destructuring/README.md)), into bindings each
  initialized once, and the expansion is initialization, not reassignment, so
  it sets `isMutable` on none of them. `types/stack_walk`'s `walkFold` opens
  with one, the first refusal that keeps the module `.f.mjs`
  ([the leaf table](../../todo/fjs-nanvm-integration.md#current-leaf-migration-fixed-point)).
  Destructuring *assignment*, `[a, b] = …` without a declaration, is not part
  of this extension; a proposal of its own would have to make its case.

The [FAST binding contract](../../fjs/todo/compiler-vocabulary-and-modularization.md#fast-contract)
owns the shared representation and analysis. FAST uses `isMutable` for both
variables and arguments, with no separate `let`/`const` forms. Destructured
arguments become ordinary local bindings before analysis. Source declaration
legality is checked separately before discarding declaration kinds; the flag
does not authorize source `const` writes. This policy supersedes the earlier
proposal to reject every source `let` capture regardless of writes.

```js
let x = 1;
const f = () => x; // allowed: x is never reassigned
const g = a => () => a; // allowed: the same rule for parameters
```

```js
let x = 5;
x = 6;
const bad = () => x; // rejected: mutable binding captured
const snapshot = x;
const good = () => snapshot;
```

```js
const g = a => {
    const snapshot = a;
    const f = () => snapshot;
    a = 5;
    return f;
};
```

The rule replaces the first stage's post-loop `const` treatment: such a
binding remains mutable after its last assignment or loop; there is no
flow-sensitive freeze, and a function after the loop reads a snapshot. The
first stage's admission of a function called where it is written stays, as
above.

After write/capture analysis and source admission, FAST normalization maintains
a map from resolved source bindings to current immutable FAST values.
Assignment establishes a fresh value and updates that map.
Retain a required initializer even when its value is unused or overwritten.
At a branch, return the current values of outer mutable bindings assigned in
either arm; an unchanged arm supplies the preceding value. A returning or
failing arm supplies no normal branch result. Use resolved binding-introduction
order for stable result signatures.

#### General loops

Milestone H admits ordinary `while`, break, continue, and return/throw inside
loops, including sequential loops, loops in either conditional arm, nested
loops and loops at module level. Labels and other loop syntaxes such as `for`
remain separate extensions.

AST-to-FAST owns these rules:

- Resolve transfers to their owning loop or source function before lowering.
- Select all outer bindings classified `isMutable` that are read or assigned
  by the loop as its ordered parameter list, including uses in nested structured loops.
  Use that same list for normal source-loop results; this simple policy
  requires no global liveness analysis. Loop-local declarations stay local.
  Immutable outer values remain ordinary references.
- Initialize those parameters from the current binding map at the loop's
  execution point. Use break results to update that map after normal completion.
- Normalize `while (condition) { BODY }` to a core loop whose first action
  exits on `!condition`. Evaluate the condition once per reached iteration,
  including the first; continue and body-end fallthrough transfer current state
  to the next test.
- Keep the original condition/body scopes. A break supplies normal loop
  results; following statements stay after the loop. A return exits its
  owning source function; an ordinary nested source function owns its returns.

Conceptually:

```js
while (true) {
    if (!condition) { break; }
    BODY
}
```

This is an illustration of the control flow, not a text-splicing rule.
Actual output is [normalized FAST](../../fjs/todo/compiler-vocabulary-and-modularization.md#fast-contract).
Generated recursion is the [graph-construction owner's](../../fjs/edag/todo/fast-loop-construction.md)
responsibility. Source admission does not inspect helper state packages or
completion tags.

#### Benefits and costs of the extension

General rebinding and loops preserve familiar JavaScript source forms while
lowering to immutable values and explicit state. Uniform capture refusal
prevents mutable bindings from escaping through function frames.

The costs are whole-scope write/capture classification and explicit
branch/loop results. The capture restriction rejects some valid JavaScript,
captures after the last write among them, and requires migration of the old
post-loop exception.
Never-reassigned `let` bindings have the same capture behavior as unwritten
parameters; their source declaration spelling imposes no extra restriction.
