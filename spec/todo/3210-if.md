## The `if` statement, terminating

**Priority:** P2
**Status:** open

**Approval:** none yet. A language feature needs formal, explicit approval
from a language designer other than the proposer before implementation
([DESIGN.md §12](../../doc/DESIGN.md#new-language-features-start-with-a-todo));
record the approver and a link to the approval here.

### Problem

The language branches only in an expression: `?:` and the short-circuit
operators are in the language ([operators](../README.md#operators)), and a
function body is `const` statements and one terminating statement, `return`
or `throw` ([functions](../README.md#functions)). The repository's own code
is not written that way. Its modules branch with `if` as a *guard* — test,
then `return` or `throw`, then go on:

```js
export const unwrap = ([kind, v]) => {
    if (kind === 'error') { throw v }
    return v
}
```

At `f2ca9262`, 121 of the 187 `module.f.mjs` files under `fjs/` hold an
`if`, `fjs/asserts` among them, and every module above `fjs/asserts` — 165
of the 187 — waits on it. With `throw` in the language
([functions](../README.md#functions)), `if` is the next statement the
migration to `.f.js` needs
([fjs-nanvm-integration](../../todo/fjs-nanvm-integration.md#repository-compiler-compatibility-migration)).

The design question is settled everywhere but in one place.
[edag-stage1-discussion](../../todo/edag-stage1-discussion.md) fixes that
the EDAG has no statement nodes — `?:` is the branch node, and an `if` in
the language is surface syntax that lowers to it — and leaves open which
graph `if (!ok) throw e; return v` lowers to, branch-on-result or
guard-then-result, since hash-as-written makes two graphs two functions.
This proposal closes that question by admitting the one form of `if` that
has one lowering.

### Proposal

`if (condition) block` is a statement in a function's block body, standing
where a `const` statement may, any number of times, before the body's
terminating statement. Its block is the block the grammar already has, `{`
any number of `const` statements and one terminating statement `}`, so
the branch always ends in `return` or `throw`, and the statements after the
`if`, up to and including the body's own terminator, are what runs when the
condition is falsy.

```text
block     ::= '{' statement* terminator '}'
statement ::= const | 'if' '(' value ')' block
```

```js
export const unwrap = r => {
    if (r[0] === 'error') { throw r[1]; }
    return r[1];
};
export const assert = (v, msg) => {
    if (v) { return undefined; }
    throw msg ?? 'assertion failed';
};
export const sign = n => {
    if (n < 0) { return -1; }
    if (n > 0) { return 1; }
    return 0;
};
```

Everything else is JavaScript's, read as the specification reads `return`
and `throw`:

- **The condition is any expression**, evaluated where the statement
  stands — after the `const`s before it and before anything after it — and
  tested as `?:` tests its condition, by JavaScript's
  [truthiness](https://developer.mozilla.org/en-US/docs/Glossary/Falsy).
- **The braces are required.** JavaScript also admits a bare statement,
  `if (c) return v;`, and the repository writes it, `if (!v) throw msg` in
  `fjs/asserts`. Refusing it protects no language guarantee; it is a design
  decision of this proposal, made knowing the cost, and
  [DESIGN.md §12](../../doc/DESIGN.md#12-preserve-harmless-javascript-conventions)
  asks that the reason be stated. The reason is that the block is where
  the language's scoping happens: a branch may hold `const`s, and the `{`
  `}` is what says which statements those `const`s are visible to and
  which arm an anchor belongs to. One block form means one shape for the
  syntax tree, the lowering and the reader; the bare form is that block
  with one statement and no fence, and it is the form whose extension is
  the classic mistake, a second statement written under the `if` and
  parsed outside it. The cost is one edit per bare guard, adding the
  braces, which the migration makes anyway. Admitting the bare form later
  is additive.
- **The block terminates.** A block that falls off its end is refused
  already, and the reason holds here with more force: in a language without
  mutation, a branch that does not `return` or `throw` can only declare
  `const`s that nothing after the block can name, which is dead code.
- **There is no `else`, for now.** `if (c) { return a; } else { return b; }`
  is `if (c) { return a; } return b;`, and an `else if` chain is a sequence
  of guards, as `sign` above: the statements after a guard are its `else`
  branch already, so `else` names nothing the body cannot say. Where `else`
  would stand, only two forms are JavaScript. An `else` block that does not
  terminate is the fall-through block the previous bullet excludes. An
  `else` block that terminates is harmless when the whole `if … else` is
  the body's last statement — nothing follows, both arms terminate, and it
  lowers to the same `?:` — but it is then a terminator of its own, a third
  terminating statement beside `return` and `throw`, with its `else if`
  chain to spell in the grammar and a second place for a block's anchors to
  be placed. This proposal protects no guarantee by leaving it out; it
  defers it, as it defers the module-level guard, because the guard alone
  reaches every body and the migration needs nothing more. Admitting the
  terminating `else` later is additive, and until then it is refused with
  a message that says to drop the `else` and keep its block's statements.
- **No `;` after the `}`.** As in JavaScript, a block statement needs no
  terminator, and the next statement may begin on the same line. A `;`
  there is an empty statement, which the language refuses as it refuses `;;`
  ([module structure](../README.md#module-structure)).
- **Not at module level, for now.** JavaScript admits a top-level `if`, and
  a module is a function ([a module is a
  function](../README.md#a-module-is-a-function)), but `export` cannot stand
  in a block and `return` is not JavaScript there, so the only module form
  is a guard that throws, `if (c) { throw v; }`, above the exports — and the
  module's root is where the linker reads the export list from, which a
  `?:` above it would hide. That is a proposal of its own, with the linker's
  reading in it; until then a module-level `if` is refused at `if`, as any
  statement beginning with a value is.

**Lowering.** `if` never extends the EDAG. A body `s… if (c) B rest`
lowers to `['?:', c, ⟦B⟧, ⟦rest⟧]`: the condition, the block's value, and
the value of the remaining statements lowered by the same rule — so a second
`if` nests as the alternate of the first, and the body's terminator is the
innermost alternate. Branch-on-result is the canonical graph; there is no
guard-then-result form to choose against, since the block's own terminator
is the result.

Where a `const` lives is nothing but which edges reach it, and the rule is
the one the language already applies to a `const` under a lazy operand
([operators](../README.md#operators)):

- **A `const` before the `if`** is a node of the scope, reached from the
  scope's root as today. One that only an arm reads is anchored at the
  root's comma, evaluated eagerly, which is where JavaScript evaluates it: a
  `const` above the `if` runs before the condition does.
- **A `const` in the block, or after the `if`,** has no eager edge from the
  scope's root, because only the statements of its own arm can name it. A
  used one needs nothing done. An unused one is anchored at a comma at its
  arm — the arm is its block root — and never at the scope's root:
  JavaScript never evaluates it when the other arm is taken, and evaluating
  it there would fail where JavaScript returns.

That is exactly the graph a parameterless function called where it is
written lowers to ([functions](../README.md#functions)), so an `if` and the
conditional-with-block spelling of the same body are one graph:

```js
(a) => { if (a) { const x = [1]; return [x, x]; } return 0; }
(a) => a ? (() => { const x = [1]; return [x, x]; })() : 0
```

both lower to `['=>', 1, null, ['?:', ['arg', 0], ['[]', [x, x]], 0]]` with
`x` the one shared node `['[]', [1]]`. The pinned graphs the proofs assert,
each the graph the compiler produces today for the second spelling:

|Body|Graph|
|----|-----|
|`const a = [1]; if (m) { return a; } return 0;`|`[',', [a, ['?:', m, a, 0]]]`|
|`const a = [1]; if (m) { return a; } return a;`|`[',', [a, ['?:', m, a, a]]]`|
|`if (a) { throw 1; } const y = [2]; return y;`|`['?:', a, ['throw', 1], ['[]', [2]]]`|
|`if (a) { throw 1; } const z = [2]; return 1;`|`['?:', a, ['throw', 1], [',', [['[]', [2]], 1]]]`|

The first row is the anchoring rule: `a` is reached only through the
consequent, so the root's comma evaluates it first, as JavaScript does. The
second row is the same, and `m ? a : a` is not folded to `a`: the EDAG
mirrors the source, and the condition is an evaluation of its own that may
fail. The third row has `y` reached from the alternate alone, no anchor
anywhere. The fourth has `z` anchored at the alternate's comma, not the
function's root.

**Outputs.** No writer changes. `if` is never written: the FunctionalScript
writer spells a `?:` as the conditional operator and a value shared under
one lazy operand alone in a block opened at the operand, the parameterless
function it already writes ([functions](../README.md#functions)), so the
third row writes back as `$a_0?(()=>{throw 1;})():[2]` and the example
above as `$a_0?(()=>{const $b0=[1];return [$b0,$b0];})():0`. Reading either
back gives the graph that was written; round trip is graph identity, not
text identity, as it is for `-1` and for a body `const` renamed in a block.
The EDAG output carries the `?:`, the Rust output prints it as it prints
any conditional, and the value outputs refuse an operator as they do today.
Writing a `?:` at a block's terminator as an `if`, for a reader's sake, is
a later improvement of the writer that changes text and no graph.

**Hash.** One graph, one hash: `if` is syntactic sugar over `?:`, and a
module hashes the same however its guards are spelled.

**Benefits.** The guard is the shape the repository is already written in,
so the migration proceeds by renaming rather than rewriting. `assert` needs
no `!`: `if (v) { return undefined; } throw msg;`. The lowering question the
stage-1 discussion left open is closed, by construction rather than by
convention. And the feature touches the parser and the fold alone: no EDAG
node, no evaluator, no analysis handler, no writer, no Rust printer case and
no corpus group.

**Drawbacks.** It is a restricted `if` — braces required, the block
terminating, no `else`, none at module level — and each restriction is one
JavaScript admits, justified above and additive to lift. Two source
spellings denote one graph, the guard and the conditional, as `value` and
`{ return value; }` already do; the writer picks the conditional, so a
module written with guards reads back without them. A reader who writes
`else` or a bare `if (c) return v;` meets a refusal, which must name what
the language wants instead.
